# HCS 首次全量与增量衔接

当前 `scan.startup.mode=incremental` 只读取复制槽保留的增量。不能简单在它前面增加
`SELECT *`：全量查询期间仍有写入，若没有与该查询一致的复制流边界，就可能漏掉写入，
或先发全量新值再回放边界前的旧变更，使下游数据回退。

## 可执行的停写交接流程

首次全量可由客户自己的 JDBC 导数程序完成；本仓库的 Flink CDC 2.3 连接器只负责
后续增量。此方式要求业务接受一个覆盖全量扫描和建槽的维护窗口：

1. 在目标 PDB 的所有写节点暂停业务写入及会修改目标表的 DDL，并等待在途写事务结束。
2. 用普通 JDBC 读取所需表的全量，把结果可靠地提交到与增量相同的下游。导数失败则保持
   停写并重做全量，不进入下一步。
3. **仍在停写期间**，由管理员在同一个 PDB 新建专用的
   `parallel_json_decoding` 逻辑复制槽；核对槽名、插件和未被其他任务消费。
   建槽 SQL 见[实例前置条件](HCS_INSTANCE_PREREQUISITES.md)。若 PDB 已有其他作业的槽，
   不得直接删除或复用；需先由管理员确认槽配额及作业归属。
4. 用 `scan.startup.mode=incremental` 启动当前连接器，确认复制流已启动、槽持续保留、
   Flink checkpoint 正常。随后恢复业务写入；恢复后的变更从新槽读取。

关键条件是**从步骤 1 到步骤 3 建槽成功期间没有任何目标业务写入**。
复制槽可以在 JDBC 全量之前创建，也可以在全量完成之后创建；但后一种顺序只有在
停写始终覆盖整段间隔时才安全。`xlog_position` 是建槽位置，不需要把单段值伪造成
三段快照位点；当前增量连接器从专用新槽的可用起点开始。任务启动前若恢复了写入，
槽仍须保留足够 WAL，不得被其他消费者推进。

若全量期间或全量与建槽之间发生过写入，当前连接器没有经过验证的 HCS 接口回放
建槽前的变更；不能靠 `0/0,0/0,0/0` 或当前槽位点补出这段历史。除非产品方明确
提供并验证 HCS 历史解码流程，否则应停写、清理本次不完整的下游全量结果，
再完整重做交接。不能只补建槽后继续。

## 尚须在目标 HCS 实例确认的边界

本地产品文档的**通用系统函数**条目有 `pg_export_snapshot_and_csn()` 的说明，
称其返回快照标识和 CSN；透明多写逻辑复制章节未给出该函数的用法。尚未证明它在
HCS 507 透明多写 PDB 可用，也未说明其 CSN 和三段复制位点的
等值边界、跨写节点顺序以及快照事务崩溃后的恢复规则。不能用单个 CN/DN 的 WAL LSN
代替全局边界。还需确认快照事务能否跨多个扫描 SQL 保持同一个一致视图；文档的
`pg_export_snapshot()` 条目同时提示部分 GaussDB 部署不支持所需的隔离级别。

产品文档中的 `gs_txn_lsn_time`、`restart-lsn` 指定位点示例归在**非透明多写**
逻辑解码章节；它们不能证明透明多写支持按该方式从建槽前的历史日志恢复。
`pg_create_logical_replication_slot` 返回的 `xlog_position` 是建槽时的位置，
不是与稍后全量查询绑定的三段复制位点。`withStartPosition` 选择解码开始位置，
不会使 SQL 扫描自动获得该位置对应的一致视图。

只读探针可以在内网执行，不会建槽、删槽、启动复制流、发送 ACK 或读业务表：

```bash
java -cp target/gaussdb-flink-cdc-2.3-0.1.0-SNAPSHOT-all.jar \
  com.ververica.cdc.connectors.gaussdb.examples.HcsSnapshotBoundaryDiagnostics \
  /secure/path/hcs.properties
```

它会显示现有槽的实际列、实例是否接受 `REPEATABLE READ`、事务隔离级别，
以及 `pg_export_snapshot_and_csn()` 的返回值或错误。即使函数不可用，探针仍会输出
前面的诊断结果。函数存在本身也不证明上述衔接语义成立。

**不停写**的在线首次全量只有在边界和恢复语义经产品方及真机验证后才能开放。实现还须覆盖
全量中途故障、checkpoint/savepoint 恢复、扫描期间 INSERT/UPDATE/DELETE、
大表分批和复制槽 WAL 保留压力；现阶段不把已有增量模式伪装成全量模式。
